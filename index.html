1

Banco de dados relacional vs. NoSQL

Aula 1 · [SIS]ANO2C1B3S17A1

Conceitos-chave

Banco de dados relacional (SQL): organiza os dados em tabelas com esquema fixo (colunas e tipos definidos), relacionadas entre si por chaves primárias e estrangeiras. Garante propriedades ACID (Atomicidade, Consistência, Isolamento, Durabilidade), o que o torna ideal para dados que exigem forte integridade e consistência transacional. Exemplos: MySQL, PostgreSQL, SQL Server, Oracle.

Banco de dados NoSQL: não segue o modelo tabular fixo; o esquema é flexível ou inexistente, o que facilita lidar com dados heterogêneos e permite escalabilidade horizontal (adicionar mais servidores em vez de aumentar a capacidade de um só). Geralmente prioriza disponibilidade e desempenho em grande escala, muitas vezes seguindo o modelo BASE (Basicamente disponível, estado Suave, consistência Eventual) em vez de ACID estrito.

Categoria NoSQLComo armazenaExemplosUso típico
DocumentosDocumentos JSON/BSON aninhadosMongoDB, FirestoreCatálogos, perfis de usuário, conteúdo dinâmico
Chave-valorPares chave → valorRedis, DynamoDB, Firebase Realtime DBCache, sessões, dados em tempo real
ColunarFamílias de colunas, otimizado p/ escrita massivaCassandra, HBaseSéries temporais, logs, IoT
GrafosNós e arestas (relacionamentos)Neo4jRedes sociais, recomendação
Regra prática: se o sistema precisa de transações financeiras confiáveis e relações bem definidas entre entidades, pense relacional. Se precisa de alta escalabilidade horizontal, dados heterogêneos ou sincronização em tempo real, pense NoSQL.

Respondendo às questões da atividade

Aplicando o comparativo a quatro cenários representativos, cobrindo os pontos pedidos: tipo de banco mais adequado, desafios, exemplos de operações e impacto no longo prazo.

Cenário A — Sistema bancário
Controle de contas, saldos e transferências entre clientes.
Cenário B — Catálogo de e-commerce
Produtos com atributos variáveis por categoria (roupa tem tamanho/cor, eletrônico tem voltagem/garantia).
Cenário C — Chat / feed social em tempo real
Mensagens e atualizações que precisam aparecer instantaneamente em vários dispositivos.
Cenário D — Telemetria de sensores IoT
Milhares de leituras de temperatura/localização por segundo, para análise histórica.
Pergunta 1 — Tipo de banco mais adequado e justificativa

RelacionalCenário A (bancário): exige ACID — uma transferência precisa debitar de uma conta e creditar em outra de forma atômica, sem estados intermediários inconsistentes. PostgreSQL/MySQL garantem isso nativamente com transações e chaves estrangeiras.

NoSQL — DocumentosCenário B (catálogo): cada produto tem atributos diferentes; forçar isso em tabelas fixas gera muitas colunas vazias ou tabelas auxiliares complexas. Um banco de documentos (MongoDB/Firestore) permite que cada item tenha sua própria estrutura.

NoSQL — Chave-valor / tempo realCenário C (chat/feed): o requisito central é latência baixíssima e sincronização multi-dispositivo, algo que bancos como Firebase Realtime Database resolvem nativamente com listeners em tempo real.

NoSQL — ColunarCenário D (IoT): volume de escrita altíssimo e dados sequenciais por tempo; Cassandra escala horizontalmente para suportar milhões de inserções sem gargalos.

Pergunta 2 — Desafios de cada tipo de banco no contexto apresentado
  • Bancário (relacional): escalar horizontalmente é mais difícil (sharding é complexo); picos de acesso simultâneo podem gerar contenção de locks nas tabelas mais acessadas.
  • Catálogo (documentos): falta de esquema fixo pode levar a inconsistência de dados entre documentos (campos digitados de forma diferente); consultas complexas que cruzam várias coleções são menos eficientes do que um JOIN relacional.
  • Chat/feed (tempo real): manter conexões abertas em escala consome mais recursos de servidor; conflitos de escrita simultânea exigem estratégia explícita de resolução.
  • IoT (colunar): modelar as "queries" de consulta com antecedência é necessário (o banco é otimizado para os padrões de leitura previstos); alterar esses padrões depois costuma exigir redesenhar a tabela.
Pergunta 3 — Exemplos de operações em cada banco

Relacional (SQL) — transferência bancária:

BEGIN TRANSACTION;
UPDATE contas SET saldo = saldo - 200 WHERE id_conta = 1;
UPDATE contas SET saldo = saldo + 200 WHERE id_conta = 2;
COMMIT;

NoSQL documentos (Firestore) — adicionar produto ao catálogo:

db.collection("produtos").add({
  nome: "Tênis Runner",
  categoria: "calçados",
  atributos: { tamanho: 42, cor: "preto" },
  preco: 249.90
});

NoSQL chave-valor (Realtime DB) — nova mensagem de chat:

firebase.database().ref('chats/sala1/mensagens').push({
  autor: "Giovanna",
  texto: "Oi, tudo bem?",
  timestamp: Date.now()
});

NoSQL colunar (Cassandra) — inserir leitura de sensor:

INSERT INTO leituras_sensor (sensor_id, timestamp, temperatura)
VALUES ('sensor-42', toTimestamp(now()), 23.7);
Pergunta 4 — Impacto da escolha no desempenho e na manutenção a longo prazo

A escolha do banco de dados é uma decisão arquitetural difícil de reverter. Bancos relacionais tendem a manter alta consistência e facilidade de auditoria conforme o sistema cresce, mas exigem planejamento cuidadoso de índices e, eventualmente, técnicas de particionamento para continuar performáticos — a manutenção do esquema (migrations) também fica mais rígida. Bancos NoSQL escalam horizontalmente com mais naturalidade e acompanham bem o crescimento de tráfego e volume, mas a ausência de um esquema fixo pode acumular dívida técnica de dados (inconsistências, duplicidade) se a equipe não impuser convenções; consultas analíticas complexas também tendem a exigir ferramentas adicionais (ex.: BigQuery, Elasticsearch) no longo prazo. Em muitos sistemas reais, a solução madura é híbrida: relacional para o núcleo transacional e NoSQL para os módulos de alto volume ou tempo real.

Firebase para armazenamento de dados

Aula 2 · [SIS]ANO2C1B3S17A2

O que é o Firebase

O Firebase é uma plataforma BaaS (Backend as a Service) do Google que oferece bancos de dados NoSQL gerenciados na nuvem, autenticação, armazenamento de arquivos, hospedagem e mais — sem que o desenvolvedor precise administrar servidores. Para armazenamento de dados, o Firebase oferece dois produtos:

Cloud FirestoreRealtime Database
EstruturaColeções de documentos (parecido com JSON, permite subcoleções)Uma única árvore JSON gigante
ConsultasConsultas compostas e indexação avançadaConsultas simples, um nível por vez
TransaçõesTransações atômicas entre múltiplos documentosSem suporte nativo a transações multi-registro
EscalabilidadeEscala horizontalmente de forma automáticaMelhor para volumes menores e sync em tempo real simples
Uso off-lineCache local completo com sincronização automáticaPersistência off-line com limitações (sem consulta off-line)

Na prática, o Firestore é hoje a opção recomendada pelo Google para a maioria dos apps novos, e o Realtime Database continua útil quando o requisito central é latência mínima em atualizações simples (ex.: indicador de "usuário digitando...", presença online).

Estudo de caso: aplicativo de receitas

Um app permite que usuários criem, editem, consultem e excluam receitas culinárias, com sincronização entre celular e tablet, inclusive quando o usuário está sem internet no meio de uma compra no mercado.
Pergunta 1 — Como configurar o Firebase para criação e sincronização de receitas
1
Criar um projeto no Console do Firebase e registrar o app (Android/iOS/Web), adicionando o arquivo de configuração (google-services.json ou SDK config).
2
Ativar o Cloud Firestore e criar a coleção receitas, com documentos contendo campos como titulo, ingredientes (array), modoPreparo, tempoPreparoMin, categoria, autorId e criadoEm.
3
Ativar o Firebase Authentication para identificar o autor de cada receita e controlar quem pode editar/excluir.
4
Configurar o Firebase Storage para as fotos das receitas, salvando na receita apenas a URL da imagem.
5
Habilitar a persistência off-line do SDK (enableIndexedDbPersistence na Web ou habilitada por padrão em Android/iOS), permitindo criar/editar receitas sem internet — o SDK sincroniza automaticamente assim que a conexão retorna.
6
Definir Security Rules restringindo escrita apenas ao autor autenticado e leitura pública (ou por grupo, conforme a regra de negócio).
Pergunta 2 — Implementação das operações CRUD

Create — adicionar nova receita:

import { collection, addDoc, serverTimestamp } from "firebase/firestore";

await addDoc(collection(db, "receitas"), {
  titulo: "Bolo de cenoura",
  ingredientes: ["3 cenouras", "2 xícaras de farinha", "1 xícara de açúcar"],
  modoPreparo: "Bata tudo no liquidificador e asse por 40 minutos.",
  tempoPreparoMin: 50,
  categoria: "sobremesa",
  autorId: auth.currentUser.uid,
  criadoEm: serverTimestamp()
});

Read — listar receitas em tempo real (atualiza a tela automaticamente quando algo muda):

import { collection, query, where, onSnapshot } from "firebase/firestore";

const q = query(collection(db, "receitas"), where("categoria", "==", "sobremesa"));
onSnapshot(q, (snapshot) => {
  const receitas = snapshot.docs.map(doc => ({ id: doc.id, ...doc.data() }));
  atualizarTela(receitas);
});

Update — editar uma receita existente:

import { doc, updateDoc } from "firebase/firestore";

await updateDoc(doc(db, "receitas", receitaId), {
  tempoPreparoMin: 45,
  ingredientes: ["3 cenouras", "2 xícaras de farinha", "1 xícara de açúcar", "1 colher de fermento"]
});

Delete — remover uma receita:

import { doc, deleteDoc } from "firebase/firestore";

await deleteDoc(doc(db, "receitas", receitaId));

Como a persistência off-line está ativada, essas quatro chamadas funcionam normalmente mesmo sem internet: o SDK grava localmente e enfileira a operação para sincronizar com o servidor assim que a conexão voltar — o mesmo princípio de filas de operações estudado na Aula 3.

Pergunta 3 — Possíveis desafios: limitação de consultas e custo
  • Consultas compostas exigem a criação manual de índices compostos no console; sem isso, a consulta simplesmente falha em produção.
  • O Firestore não tem busca textual nativa (ex.: buscar "bolo" dentro do modo de preparo) — para isso é preciso integrar um serviço externo como Algolia ou Typesense.
  • Custo por leitura/escrita: o plano gratuito (Spark) do Firebase inclui cerca de 50 mil leituras, 20 mil gravações e 20 mil exclusões por dia e 1 GiB de armazenamento; no plano pago (Blaze), cada 100 mil leituras acima do limite gratuito custam cerca de US$ 0,06. Uma tela que recarrega a lista inteira de receitas a cada abertura pode consumir a cota rapidamente conforme o app cresce.
  • Diferente de bancos relacionais, o Firebase não tem um teto de gastos automático — apenas alertas de orçamento, que podem chegar horas depois de o custo já ter disparado, algo que a equipe precisa monitorar ativamente.
  • Documentos têm limite de tamanho (1 MiB), o que restringe receitas com muitas imagens ou textos muito longos incorporados diretamente no documento.
Pergunta 4 — Como o Firebase facilita o desenvolvimento de apps com dados dinâmicos

O Firebase elimina a necessidade de construir e manter um backend próprio (servidor, API, infraestrutura de banco): autenticação, banco de dados, armazenamento de arquivos e hospedagem já vêm prontos e integrados. Os listeners em tempo real (onSnapshot) atualizam a interface automaticamente sempre que os dados mudam — sem precisar programar polling ou WebSockets manualmente — o que é exatamente o comportamento desejado em um app de receitas colaborativo, onde a lista deve refletir novas receitas de outros usuários instantaneamente. Somado à persistência off-line automática, isso permite que uma equipe pequena entregue um app funcional, dinâmico e sincronizado entre dispositivos muito mais rápido do que construindo tudo do zero.

Sincronização de dados off-line

Aula 3 · [SIS]ANO2C1B3S17A3
Situação disparadora: uma startup criou um app de gestão de pedidos para restaurantes que funciona off-line em áreas de infraestrutura limitada. Ao sincronizar no fim do dia, surgiram pedidos duplicados, dados sobrescritos entre dispositivos e sincronizações parciais — gerando atraso no preparo, clientes insatisfeitos e prejuízo financeiro.

A sincronização off-line exige equilibrar três forças: consistência, disponibilidade e eficiência. A técnica ideal depende do volume de dados, da frequência de atualizações e da probabilidade de conflitos.

Técnicas de sincronização

TécnicaComo funcionaVantagemDesvantagem
Armazenamento local com sincronização periódicaDados salvos localmente (SQLite, Room, Realm) e sincronizados em intervalos definidos ou quando há conexãoSimples de implementar; reduz carga no servidorPode gerar inconsistências se os dados locais ficarem desatualizados
Filas de operações (operation queues)Cada ação (criar/atualizar/excluir) vira uma entrada em fila, processada em ordem ao voltar onlineGarante ordem das operações; evita duplicidadeComplexidade em filas grandes ou falhas de processamento
Sincronização baseada em eventosMudanças disparam eventos em tempo real (WebSockets, Firebase, MQTT); off-line, eventos ficam guardados localmenteAtualização em tempo real; feedback imediatoConsome mais recursos; não ideal para grandes volumes
Sincronização diferencial (delta sync)Sincroniza apenas o que mudou, não o conjunto completoReduz tráfego de rede; mais rápidaMaior complexidade de implementação
Sincronização bidirecionalAlterações ocorrem tanto no cliente quanto no servidor, unificando os dois ladosFlexível; ideal para apps colaborativosMais suscetível a conflitos

Gerenciamento de conflitos

Conflitos surgem quando o mesmo dado é alterado em locais diferentes sem que um saiba do outro. Os dois tipos mais comuns são conflito de escrita simultânea (dois dispositivos editam o mesmo registro off-line) e conflito de exclusão (um dispositivo exclui um registro que outro tenta atualizar).

EstratégiaComo resolveExemplo
Última edição prevalece (last-write-wins)O registro com timestamp mais recente substitui os anterioresEdição simultânea de endereço: a mais recente é salva
Resolução manualO próprio usuário escolhe qual versão manterApp de calendário mostra dois horários conflitantes para o usuário decidir
Fusão automática (merge)Combina as alterações em uma nova versãoApp de notas mescla duas edições distintas em um único texto
Versões paralelasMantém os registros conflitantes separados, com tags de origem/timestampApp de documentos guarda duas versões de um arquivo editado ao mesmo tempo

Exemplos práticos

  • App de pedidos on-line: cada pedido recebe um UUID (identificador único universal) gerado no cliente, o que evita duplicidade e conflitos na sincronização — resolveria diretamente o problema da startup de restaurantes do início da aula.
  • App de saúde: enfermeiros em campo registram dados de pacientes off-line; se dois profissionais atualizarem o mesmo paciente, o app aplica resolução no cliente exibindo uma fusão dos dados.
  • Gestão de inventário: usa sincronização diferencial, enviando ao servidor apenas os itens alterados, não a lista completa.
Solução para o cenário do restaurante: combinar UUID por pedido (evita duplicidade) + fila de operações (garante ordem) + sincronização baseada em eventos quando há conexão parcial, com last-write-wins para campos simples e resolução manual apenas para conflitos de pagamento, que são sensíveis demais para resolver automaticamente.

Criptografia de dados

Aula 4 · [SIS]ANO2C1B3S17A4
Contexto: aplicativo que armazena dados sensíveis de pacientes (prontuários, diagnósticos) e precisa protegê-los tanto durante a transmissão quanto quando armazenados no banco de dados.

Criptografia simétrica vs. assimétrica

SimétricaAssimétrica
ChavesUma única chave, usada para cifrar e decifrarPar de chaves: pública (cifra) e privada (decifra)
VelocidadeRápida, ideal para grandes volumes de dadosMais lenta, custosa computacionalmente
Algoritmos comunsAES-256, ChaCha20RSA, ECC (curvas elípticas)
Desafio principalDistribuir e proteger a chave compartilhada com segurançaGerenciar o par de chaves e a autenticidade da chave pública
Uso típicoCriptografar dados em repouso (banco de dados, arquivos)Troca segura de chaves, assinatura digital, autenticação (certificados TLS)
Pergunta 1 — Como implementar criptografia simétrica e assimétrica no aplicativo
  • Simétrica (AES-256): usada para cifrar os dados sensíveis antes de gravá-los no banco (ex.: campo diagnostico de um prontuário). A chave AES fica protegida em um cofre de chaves gerenciado (Android Keystore, iOS Keychain, ou um serviço como Google Cloud KMS / AWS KMS) — nunca embutida no código-fonte.
  • Assimétrica (RSA/ECC): usada em dois momentos — (1) no handshake TLS, quando o app se conecta ao servidor, para autenticar o servidor e combinar uma chave de sessão simétrica com segurança; e (2) para assinatura digital, garantindo que um laudo médico não foi alterado após ser emitido pelo profissional responsável.
  • Abordagem híbrida (a mais usada na prática): a criptografia assimétrica troca a chave com segurança; toda a comunicação de dados em si é cifrada com a chave simétrica resultante — é exatamente assim que o próprio TLS/SSL funciona.
  • Senhas de usuários não devem ser criptografadas e sim aplicadas hash (bcrypt, Argon2, com salt), já que não precisam ser revertidas — apenas comparadas no login.
Pergunta 2 — Soluções para proteger dados em trânsito e em repouso

Em trânsito (dados percorrendo a rede entre app e servidor):

  • HTTPS/TLS obrigatório em todas as chamadas de API — nunca permitir HTTP puro.
  • Certificate pinning no app móvel, para impedir ataques do tipo "man-in-the-middle" mesmo que um certificado falso seja instalado no dispositivo.
  • Evitar canais informais e não criptografados (ex.: envio de exames por WhatsApp comum), prática ainda comum e arriscada em sistemas de saúde.

Em repouso (dados armazenados no banco/disco):

  • Encryption at rest no próprio banco de dados — o Firestore, por exemplo, já criptografa automaticamente todos os dados armazenados com chaves gerenciadas pelo Google, com opção de usar chaves gerenciadas pelo próprio cliente (CMEK) para maior controle.
  • Criptografia em nível de campo para os dados mais sensíveis (ex.: diagnóstico, CPF), cifrando o valor com AES antes de salvar, como camada extra além da criptografia do banco.
  • Controle de acesso por perfil (RBAC) combinado com Security Rules, para que só profissionais autorizados leiam determinados registros.
  • Backups também criptografados — um erro comum é proteger o banco principal e esquecer os backups.
Pergunta 3 — Riscos associados à falta de criptografia no contexto médico
  • Exposição de dados sensíveis: a LGPD (Lei 13.709/2018) classifica dados de saúde como dado pessoal sensível (Art. 5º, II), sujeitos a regras mais rígidas de proteção.
  • Vazamentos são frequentes: pesquisas apontam que a maioria dos hospitais já sofreu ao menos um incidente de vazamento de dados nos últimos anos — prontuários expostos podem ser usados para fraude de identidade, chantagem ou golpes envolvendo planos de saúde.
  • Discriminação e estigmatização: diagnósticos vazados (condições psiquiátricas, doenças infecciosas, exames genéticos) podem gerar discriminação no trabalho, em seguros ou socialmente.
  • Sanções legais: a ANPD pode aplicar multas de até 2% do faturamento (limitado a R$ 50 milhões por infração) a organizações que não adotarem medidas técnicas adequadas, incluindo criptografia.
  • Perda de confiança e dano reputacional para a clínica, hospital ou desenvolvedor do aplicativo responsável pelo incidente.
Pergunta 4 — Importância de proteger os dados sensíveis dos usuários

Proteger dados sensíveis não é apenas uma exigência legal (LGPD) — é uma condição para que o usuário confie no sistema o suficiente para usá-lo de forma honesta e completa. No caso da saúde, isso é ainda mais crítico: se o paciente teme que suas informações vazem, pode omitir sintomas ou histórico, prejudicando o próprio atendimento. A criptografia, portanto, deve ser tratada como parte do design do sistema desde o início ("security by design"), e não como um adendo de última hora — protegendo tanto a privacidade individual quanto a confiabilidade e a reputação de toda a aplicação.
