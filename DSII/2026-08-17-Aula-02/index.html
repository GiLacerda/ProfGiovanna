🎓 Reutilização de Código e Refatoração

Escreva menos, aproveite mais, melhore sempre

🚀 Por Que Esses Conceitos Importam?

Reutilizar código e refatorar são duas faces da mesma moeda: evitar retrabalho e manter o código saudável ao longo do tempo.

  • Reduzir código duplicado e o risco de bugs inconsistentes
  • Acelerar o desenvolvimento de novas funcionalidades
  • Manter o sistema fácil de entender e modificar
  • Diminuir o custo de manutenção a longo prazo
  • Preparar o código para crescer sem quebrar
💡 Lembre-se: Reutilização evita que você escreva a mesma lógica duas vezes. Refatoração garante que o código continue bom depois que ele já existe.

♻️ 1. Reutilização de Código

Reutilização é a prática de usar um mesmo trecho de lógica em diferentes partes do sistema, em vez de reescrevê-lo repetidamente.

Princípio DRY

💡 DRY — Don't Repeat Yourself: toda regra de negócio deve existir em um único lugar no código. Se você precisa mudar algo em dois lugares diferentes para corrigir um único problema, há duplicação a resolver.

1.1 Extraindo Lógica Repetida em Métodos

❌ Código Duplicado

public double calcularAreaCirculo1(double raio) { return 3.14159 * raio * raio; } public double calcularAreaCilindro(double raio, double altura) { double area = 3.14159 * raio * raio; return area * altura; }

✅ Lógica Reutilizada

public double calcularAreaCirculo(double raio) { return Math.PI * raio * raio; } public double calcularVolumeCilindro(double raio, double altura) { double areaBase = calcularAreaCirculo(raio); return areaBase * altura; }

1.2 Reutilização com Herança

Compartilhando atributos e comportamentos comuns
// Classe base concentra o que é comum public class Funcionario { protected String nome; protected double salarioBase; public Funcionario(String nome, double salarioBase) { this.nome = nome; this.salarioBase = salarioBase; } public double calcularSalario() { return salarioBase; } } // Gerente reutiliza nome, salarioBase e o construtor de Funcionario public class Gerente extends Funcionario { private double bonus; public Gerente(String nome, double salarioBase, double bonus) { super(nome, salarioBase); this.bonus = bonus; } @Override public double calcularSalario() { return salarioBase + bonus; } }

1.3 Reutilização com Interfaces

Contrato comum entre classes sem parentesco
public interface Pagavel { double calcularPagamento(); } public class Funcionario implements Pagavel { private double salarioBase; public double calcularPagamento() { return salarioBase; } } public class Fornecedor implements Pagavel { private double valorContrato; public double calcularPagamento() { return valorContrato; } } // O sistema de folha de pagamento reutiliza a mesma lógica // para qualquer classe que implemente Pagavel public double calcularTotalAPagar(List itens) { double total = 0; for (Pagavel item : itens) { total += item.calcularPagamento(); } return total; }

1.4 Herança vs. Composição

Herança representa uma relação "é um". Quando essa relação não é natural, composição — uma relação "tem um" — costuma ser a escolha mais flexível.

❌ Herança Forçada

// Um carro elétrico "é um" carro, ok. public class Carro { public void ligarMotorCombustao() { ... } } // Mas carro elétrico não tem motor a combustão! // Herdar aqui obriga a herdar comportamento errado public class CarroEletrico extends Carro { // precisa sobrescrever/ignorar o que não serve }

✅ Composição

public interface Motor { void ligar(); } public class MotorEletrico implements Motor { public void ligar() { /* liga o motor elétrico */ } } public class Carro { private Motor motor; public Carro(Motor motor) { this.motor = motor; } public void ligar() { motor.ligar(); } }

1.5 Formas de Reutilização

Técnica Quando usar Exemplo
Métodos Mesma lógica usada em vários pontos calcularAreaCirculo()
Herança Relação "é um" entre classes Gerente extends Funcionario
Interfaces Contrato comum entre classes não relacionadas Pagavel
Composição Relação "tem um", comportamento trocável Carro tem um Motor
Bibliotecas/Pacotes Código reutilizável entre projetos Apache Commons, Guava
💡 Dica: "Prefira composição a herança" é uma regra clássica — herança acopla fortemente as classes, enquanto composição permite trocar comportamentos com mais liberdade.

🔧 2. Refatoração

Refatorar é reorganizar a estrutura interna do código sem alterar seu comportamento externo, tornando-o mais limpo, legível e fácil de manter.

⚠️ Regra de Ouro: Refatoração muda a forma como o código é escrito, nunca o que ele produz como resultado. Por isso, ter testes antes de refatorar é essencial.

2.1 Quando Refatorar? — Sinais de Alerta ("Code Smells")

Sinal Descrição
Código duplicado O mesmo trecho de lógica aparece em vários lugares
Método longo Uma função faz muitas coisas ao mesmo tempo
Classe inchada Uma classe concentra responsabilidades demais
Muitos parâmetros Métodos com listas enormes de argumentos
Nomes ruins Variáveis e métodos que não explicam seu propósito
Condicionais aninhados Vários "ifs" um dentro do outro, difíceis de seguir

2.2 Técnica: Extract Method (Extrair Método)

❌ Antes

public void imprimirFatura(Pedido pedido) { double total = 0; for (Item item : pedido.getItens()) { total += item.getPreco() * item.getQuantidade(); } System.out.println("=== FATURA ==="); System.out.println("Cliente: " + pedido.getCliente()); System.out.println("Total: R$ " + total); }

✅ Depois

public void imprimirFatura(Pedido pedido) { double total = calcularTotal(pedido); imprimirCabecalho(pedido, total); } private double calcularTotal(Pedido pedido) { double total = 0; for (Item item : pedido.getItens()) { total += item.getPreco() * item.getQuantidade(); } return total; } private void imprimirCabecalho(Pedido pedido, double total) { System.out.println("=== FATURA ==="); System.out.println("Cliente: " + pedido.getCliente()); System.out.println("Total: R$ " + total); }

2.3 Técnica: Renomear para Clareza

❌ Antes

public double calc(int a, int b) { return a * b * 0.1; }

✅ Depois

private static final double TAXA_COMISSAO = 0.1; public double calcularComissao(int quantidadeVendida, double precoUnitario) { return quantidadeVendida * precoUnitario * TAXA_COMISSAO; }

2.4 Técnica: Extract Class (Dividir Responsabilidades)

❌ Uma classe fazendo tudo
public class Usuario { private String nome; private String email; public boolean validarEmail() { /* ... */ return true; } public void enviarEmailBoasVindas() { /* ... */ } public void salvarNoBanco() { /* ... */ } public String gerarRelatorioPDF() { /* ... */ return ""; } }
✅ Responsabilidades separadas
public class Usuario { private String nome; private String email; // apenas dados e regras do próprio usuário } public class ValidadorEmail { public boolean validar(String email) { /* ... */ return true; } } public class EmailService { public void enviarBoasVindas(Usuario usuario) { /* ... */ } } public class UsuarioRepository { public void salvar(Usuario usuario) { /* ... */ } }

2.5 Técnica: Substituir Números Mágicos por Constantes

❌ Antes

if (idade >= 18) { liberarAcesso(); } double desconto = preco * 0.05;

✅ Depois

private static final int IDADE_MINIMA = 18; private static final double TAXA_DESCONTO = 0.05; if (idade >= IDADE_MINIMA) { liberarAcesso(); } double desconto = preco * TAXA_DESCONTO;

2.6 Técnica: Simplificar Condicionais

❌ Antes

if (usuario.getIdade() >= 18) { if (usuario.isAtivo()) { if (usuario.getSaldo() > 0) { permitirCompra(); } } }

✅ Depois

boolean podeComprar = usuario.getIdade() >= 18 && usuario.isAtivo() && usuario.getSaldo() > 0; if (podeComprar) { permitirCompra(); }

2.7 Regra dos Três

💡 Regra dos Três: na primeira vez, apenas escreva o código. Na segunda vez que precisar de algo parecido, copie e siga em frente. Na terceira vez, é hora de refatorar e extrair a lógica comum.

✅ 3. Checklist Prático

Antes de considerar o código pronto, verifique:

Categoria Verificações
Reutilização ✓ Existe lógica repetida em mais de um lugar?
✓ Essa lógica poderia virar um método?
✓ Faz sentido usar herança, interface ou composição aqui?
✓ Já existe uma biblioteca que resolve isso?
Tamanho ✓ Métodos com até 20-30 linhas?
✓ Classes com uma responsabilidade clara?
✓ Poucos parâmetros por método?
Nomenclatura ✓ Nomes explicam o propósito sem precisar de comentário?
✓ Sem abreviações confusas?
Segurança da Refatoração ✓ Existem testes cobrindo o comportamento atual?
✓ O comportamento externo continua o mesmo depois da mudança?
✓ Cada refatoração foi feita em passos pequenos?

📚 4. Exemplo Completo

Veja como aplicar reutilização e refatoração juntas:

Antes (Sem Boas Práticas)

public class P { public void proc(List> l) { double t = 0; for (Map i : l) { double p = (double) i.get("preco"); int q = (int) i.get("qtd"); if (q > 0) { t = t + p * q; } } if (t > 100) { t = t - t * 0.1; } System.out.println("Total: " + t); if (t > 500) { System.out.println("Cliente VIP!"); } } }

Depois (Com Boas Práticas)

// ==================== PROCESSAMENTO DE PEDIDOS ==================== public class ProcessadorPedido { private static final double LIMITE_DESCONTO = 100.0; private static final double TAXA_DESCONTO = 0.1; private static final double LIMITE_VIP = 500.0; public void processarPedido(List itens) { double total = calcularTotal(itens); total = aplicarDesconto(total); exibirResultado(total); } private double calcularTotal(List itens) { double total = 0; for (ItemPedido item : itens) { if (item.getQuantidade() > 0) { total += item.getPreco() * item.getQuantidade(); } } return total; } private double aplicarDesconto(double total) { if (total > LIMITE_DESCONTO) { return total - (total * TAXA_DESCONTO); } return total; } private void exibirResultado(double total) { System.out.println("Total: R$ " + total); if (total > LIMITE_VIP) { System.out.println("Cliente VIP!"); } } }
Melhorias Aplicadas:
  • ✓ Nomes descritivos (P → ProcessadorPedido, proc → processarPedido)
  • ✓ Tipos específicos em vez de Map<String, Object> (uso de ItemPedido)
  • ✓ Método dividido por responsabilidade (Extract Method)
  • ✓ Números mágicos substituídos por constantes nomeadas
  • ✓ Cada método faz apenas uma coisa
  • ✓ Comentário de seção organiza a leitura

📋 6. Referência Rápida

♻️ DRY

Não repita lógica. Cada regra deve existir em um único lugar.

🧬 Herança

Use quando existe uma relação "é um" entre as classes.

🧩 Composição

Use quando existe uma relação "tem um" e comportamento flexível.

🔧 Refatoração

Mude a estrutura, nunca o comportamento. Sempre em passos pequenos.
