🎓 Reutilização de Código e Refatoração

Escreva menos, aproveite mais, melhore sempre

🚀 Por Que Esses Conceitos Importam?

Todo sistema de software cresce com o tempo: novas telas, novas regras de negócio, novas integrações. Se cada nova necessidade for resolvida copiando e colando código existente, o projeto acumula uma dívida silenciosa — a dívida técnica — que só aparece quando já é cara demais para pagar.

Reutilização de código e refatoração são as duas ferramentas mais básicas para conter essa dívida. Reutilização evita que a mesma lógica seja escrita duas vezes; refatoração garante que o código, depois de escrito, continue saudável mesmo enquanto o sistema muda ao seu redor. Elas resolvem problemas em momentos diferentes: reutilização atua enquanto você escreve código novo, refatoração atua depois, cuidando do que já existe.

Sem esses cuidados
  • A mesma regra de negócio existe em 5 lugares diferentes
  • Corrigir um bug exige lembrar de todos os lugares e corrigir em cada um
  • Métodos gigantes que ninguém quer mexer com medo de quebrar algo
  • Toda mudança pequena demora horas por causa do medo e da confusão
Com esses cuidados
  • Cada regra de negócio vive em um único lugar
  • Corrigir um bug corrige o comportamento em todo o sistema de uma vez
  • Métodos pequenos, com nomes claros e fáceis de testar
  • Novas funcionalidades aproveitam o que já existe em vez de recomeçar do zero

O custo real de ignorar esses conceitos

Estudos e experiências de mercado mostram que a maior parte do custo de um software não está em escrevê-lo pela primeira vez, e sim em mantê-lo ao longo dos anos: corrigir bugs, adicionar funcionalidades, adaptar a regras de negócio novas. Código duplicado e mal estruturado multiplica esse custo, porque cada mudança precisa ser replicada manualmente e cada parte mal organizada aumenta a chance de erro humano. Investir tempo em reutilização e refatoração hoje é, na prática, reduzir o custo de todas as mudanças futuras.

♻️ Reutilização de Código

Reutilização é a prática de usar um mesmo trecho de lógica em diferentes partes do sistema, em vez de reescrevê-lo repetidamente. Isso pode acontecer em escalas bem diferentes: reaproveitar algumas linhas dentro da mesma classe, compartilhar comportamento entre classes relacionadas, ou até reaproveitar bibliotecas inteiras escritas por outras pessoas.

Princípio DRY

💡 DRY — Don't Repeat Yourself: toda regra de negócio deve existir em um único lugar no código. Se você precisa mudar algo em dois lugares diferentes para corrigir um único problema, há duplicação a resolver.

Vale notar que DRY fala sobre duplicação de conhecimento, não apenas de texto. Dois trechos de código podem parecer parecidos sem violar DRY (coincidência), assim como dois trechos visualmente diferentes podem estar duplicando a mesma regra de negócio de formas diferentes. A pergunta certa é sempre: "se essa regra mudar, quantos lugares eu preciso tocar?". Se a resposta for mais que um, há duplicação de conhecimento a resolver.

1.1 Extraindo Lógica Repetida em Métodos

A forma mais simples de reutilizar código é extrair um trecho repetido para um método com nome claro, e chamar esse método de todos os lugares que precisam da mesma lógica.

❌ Código Duplicado

public double calcularAreaCirculo1(double raio) { return 3.14159 * raio * raio; } public double calcularVolumeCilindro(double raio, double altura) { double area = 3.14159 * raio * raio; return area * altura; }

✅ Lógica Reutilizada

public double calcularAreaCirculo(double raio) { return Math.PI * raio * raio; } public double calcularVolumeCilindro(double raio, double altura) { double areaBase = calcularAreaCirculo(raio); return areaBase * altura; }

Repare que, além de eliminar a duplicação, a versão reutilizada corrigiu um problema escondido: o valor aproximado 3.14159 poderia divergir do valor usado em outro lugar do sistema. Ao centralizar o cálculo em calcularAreaCirculo, que usa a constante Math.PI, garantimos que todo o sistema use exatamente o mesmo valor.

1.2 Reutilização com Herança

Herança permite que uma classe (subclasse) reaproveite atributos e métodos definidos em outra classe (superclasse). É útil quando existe uma relação natural de "é um" entre as classes — por exemplo, um Gerente é um Funcionário, com algumas particularidades a mais.

Compartilhando atributos e comportamentos comuns
// Classe base concentra o que é comum public class Funcionario { protected String nome; protected double salarioBase; public Funcionario(String nome, double salarioBase) { this.nome = nome; this.salarioBase = salarioBase; } public double calcularSalario() { return salarioBase; } } // Gerente reutiliza nome, salarioBase e o construtor de Funcionario public class Gerente extends Funcionario { private double bonus; public Gerente(String nome, double salarioBase, double bonus) { super(nome, salarioBase); this.bonus = bonus; } @Override public double calcularSalario() { return salarioBase + bonus; } }

Aqui, Gerente reaproveita todos os atributos e o construtor de Funcionario, e apenas sobrescreve (@Override) o comportamento que precisa ser diferente. Isso evita duplicar os campos nome e salarioBase, e a lógica que os inicializa.

💡 Cuidado: herança cria um acoplamento forte entre as classes — mudanças na superclasse afetam todas as subclasses, às vezes de formas inesperadas. Esse efeito colateral é conhecido como fragile base class problem (problema da classe-base frágil). Use herança apenas quando a relação "é um" for genuinamente verdadeira.

1.3 Reutilização com Interfaces

Quando classes não têm parentesco natural, mas precisam ser tratadas de forma parecida por outra parte do sistema, interfaces permitem definir um contrato comum sem forçar uma hierarquia de herança.

Contrato comum entre classes sem parentesco
public interface Pagavel { double calcularPagamento(); } public class Funcionario implements Pagavel { private double salarioBase; public double calcularPagamento() { return salarioBase; } } public class Fornecedor implements Pagavel { private double valorContrato; public double calcularPagamento() { return valorContrato; } } // O sistema de folha de pagamento reutiliza a mesma lógica // para qualquer classe que implemente Pagavel public double calcularTotalAPagar(List itens) { double total = 0; for (Pagavel item : itens) { total += item.calcularPagamento(); } return total; }

Funcionario e Fornecedor não compartilham uma superclasse comum além de Object, mas o método calcularTotalAPagar consegue reutilizar a mesma lógica de soma para os dois, porque ambos cumprem o contrato Pagavel. Esse é um exemplo de polimorfismo: o mesmo código funciona para tipos diferentes.

1.4 Herança vs. Composição

Herança representa uma relação "é um". Quando essa relação não é natural, composição — uma relação "tem um" — costuma ser a escolha mais flexível, porque permite trocar o comportamento em tempo de execução, sem herdar coisas que não fazem sentido.

❌ Herança Forçada

// Um carro elétrico "é um" carro, ok. public class Carro { public void ligarMotorCombustao() { } } // Mas carro elétrico não tem motor a combustão! // Herdar aqui obriga a herdar comportamento errado public class CarroEletrico extends Carro { // precisa sobrescrever/ignorar o que não serve }

✅ Composição

public interface Motor { void ligar(); } public class MotorEletrico implements Motor { public void ligar() { // liga o motor eletrico } } public class Carro { private Motor motor; public Carro(Motor motor) { this.motor = motor; } public void ligar() { motor.ligar(); } }

Na versão com composição, Carro não precisa saber se o motor é elétrico, a combustão ou híbrido — ele apenas depende da interface Motor. Isso torna o sistema mais fácil de estender: um novo tipo de motor pode ser criado sem tocar na classe Carro.

1.5 Reutilização com Generics

Em Java, generics (tipos genéricos) permitem escrever uma única classe ou método que funciona com diferentes tipos de dados, evitando duplicar a mesma estrutura para cada tipo.

❌ Uma classe por tipo

public class CaixaDeTexto { private String conteudo; public String getConteudo() { return conteudo; } public void setConteudo(String conteudo) { this.conteudo = conteudo; } } public class CaixaDeNumero { private Integer conteudo; public Integer getConteudo() { return conteudo; } public void setConteudo(Integer conteudo) { this.conteudo = conteudo; } }

✅ Uma única classe genérica

public class Caixa { private T conteudo; public T getConteudo() { return conteudo; } public void setConteudo(T conteudo) { this.conteudo = conteudo; } } // Uso: Caixa caixaTexto = new Caixa<>(); Caixa caixaNumero = new Caixa<>();

1.6 Reutilização entre Projetos: Bibliotecas e Frameworks

Nem toda reutilização acontece dentro do mesmo projeto. Muita lógica que parece nova (validação de e-mail, formatação de datas, manipulação de coleções, chamadas HTTP) já foi resolvida e testada por bibliotecas amplamente usadas, como Apache Commons, Guava ou as próprias bibliotecas padrão do Java. Antes de escrever uma solução do zero, vale perguntar: "isso já não foi resolvido por alguém?" — gerenciadores de dependência como Maven e Gradle tornam trivial incluir essas bibliotecas em um projeto Java.

💡 Dica: "Prefira composição a herança" é uma regra clássica — herança acopla fortemente as classes, enquanto composição permite trocar comportamentos com mais liberdade.

🔧 Refatoração

Refatorar é reorganizar a estrutura interna do código sem alterar seu comportamento externo, tornando-o mais limpo, legível e fácil de manter. Ou seja: para quem usa a classe ou o sistema de fora, nada muda; por dentro, o código fica mais organizado.

⚠️ Regra de Ouro: refatoração muda a forma como o código é escrito, nunca o que ele produz como resultado. Por isso, ter testes automatizados antes de refatorar é essencial — eles são a rede de segurança que garante que o comportamento não mudou.

Um bom hábito é refatorar em passos pequenos: fazer uma mudança isolada, rodar os testes, e só então seguir para a próxima mudança. Esse ciclo curto (mudar → testar → confirmar) reduz drasticamente o risco de introduzir bugs durante a refatoração, e é a mesma lógica por trás do ciclo "red-green-refactor" usado em TDD (Test-Driven Development).

2.1 Quando Refatorar? — Sinais de Alerta ("Code Smells")

"Code smell" é um termo popularizado por Martin Fowler para descrever sintomas no código que, embora não sejam bugs, indicam que algo pode estar mal projetado e provavelmente vai causar problemas conforme o sistema cresce.

Sinal Descrição
Código duplicado O mesmo trecho de lógica aparece em vários lugares
Método longo Uma função faz muitas coisas ao mesmo tempo
Classe inchada (God Class) Uma classe concentra responsabilidades demais
Muitos parâmetros Métodos com listas enormes de argumentos
Nomes ruins Variáveis e métodos que não explicam seu propósito
Condicionais aninhados Vários "ifs" um dentro do outro, difíceis de seguir
Feature Envy Um método usa mais dados de outra classe do que da própria
Data Clumps O mesmo grupo de variáveis aparece sempre junto, e deveria virar um objeto
Shotgun Surgery Uma pequena mudança de regra obriga a alterar muitos arquivos diferentes

2.2 Técnica: Extract Method (Extrair Método)

Consiste em pegar um trecho de código com um propósito claro e movê-lo para um método próprio, com nome que explique o que ele faz. É a técnica de refatoração mais usada no dia a dia.

❌ Antes

public void imprimirFatura(Pedido pedido) { double total = 0; for (Item item : pedido.getItens()) { total += item.getPreco() * item.getQuantidade(); } System.out.println("=== FATURA ==="); System.out.println("Cliente: " + pedido.getCliente()); System.out.println("Total: R$ " + total); }

✅ Depois

public void imprimirFatura(Pedido pedido) { double total = calcularTotal(pedido); imprimirCabecalho(pedido, total); } private double calcularTotal(Pedido pedido) { double total = 0; for (Item item : pedido.getItens()) { total += item.getPreco() * item.getQuantidade(); } return total; } private void imprimirCabecalho(Pedido pedido, double total) { System.out.println("=== FATURA ==="); System.out.println("Cliente: " + pedido.getCliente()); System.out.println("Total: R$ " + total); }

2.3 Técnica: Renomear para Clareza

Nomes ruins obrigam quem lê o código a "executar" mentalmente a lógica para entender o que ela faz. Um bom nome explica a intenção sem precisar de comentário.

❌ Antes

public double calc(int a, int b) { return a * b * 0.1; }

✅ Depois

private static final double TAXA_COMISSAO = 0.1; public double calcularComissao(int quantidadeVendida, double precoUnitario) { return quantidadeVendida * precoUnitario * TAXA_COMISSAO; }

2.4 Técnica: Extract Class (Dividir Responsabilidades)

Quando uma classe acumula responsabilidades que não têm relação direta entre si, ela viola o Princípio da Responsabilidade Única (Single Responsibility Principle, o "S" do SOLID). A solução é extrair cada responsabilidade para sua própria classe.

❌ Uma classe fazendo tudo
public class Usuario { private String nome; private String email; public boolean validarEmail() { return true; } public void enviarEmailBoasVindas() { } public void salvarNoBanco() { } public String gerarRelatorioPDF() { return ""; } }
✅ Responsabilidades separadas
public class Usuario { private String nome; private String email; // apenas dados e regras do proprio usuario } public class ValidadorEmail { public boolean validar(String email) { return true; } } public class EmailService { public void enviarBoasVindas(Usuario usuario) { } } public class UsuarioRepository { public void salvar(Usuario usuario) { } }

2.5 Técnica: Substituir Números Mágicos por Constantes

Um "número mágico" é um valor literal (como 18 ou 0.05) espalhado pelo código sem explicação. Dar um nome a ele documenta a intenção e evita que o mesmo valor seja digitado (e eventualmente errado) em vários lugares.

❌ Antes

if (idade >= 18) { liberarAcesso(); } double desconto = preco * 0.05;

✅ Depois

private static final int IDADE_MINIMA = 18; private static final double TAXA_DESCONTO = 0.05; if (idade >= IDADE_MINIMA) { liberarAcesso(); } double desconto = preco * TAXA_DESCONTO;

2.6 Técnica: Simplificar Condicionais

Condicionais aninhados são difíceis de acompanhar porque exigem manter várias condições "na cabeça" ao mesmo tempo. Extrair a condição composta para uma variável (ou método) bem nomeado reduz a carga mental de leitura.

❌ Antes

if (usuario.getIdade() >= 18) { if (usuario.isAtivo()) { if (usuario.getSaldo() > 0) { permitirCompra(); } } }

✅ Depois

boolean podeComprar = usuario.getIdade() >= 18 && usuario.isAtivo() && usuario.getSaldo() > 0; if (podeComprar) { permitirCompra(); }

2.7 Técnica: Substituir Loops por Stream API

No Java moderno (a partir da versão 8), a Stream API permite expressar operações sobre coleções — filtrar, transformar, somar — de forma mais declarativa, muitas vezes eliminando variáveis auxiliares e reduzindo a chance de erro em laços manuais.

❌ Antes

double total = 0; for (Item item : itens) { if (item.getQuantidade() > 0) { total += item.getPreco() * item.getQuantidade(); } }

✅ Depois

double total = itens.stream() .filter(item -> item.getQuantidade() > 0) .mapToDouble(item -> item.getPreco() * item.getQuantidade()) .sum();

2.8 Regra dos Três

💡 Regra dos Três: na primeira vez, apenas escreva o código. Na segunda vez que precisar de algo parecido, copie e siga em frente. Na terceira vez, é hora de refatorar e extrair a lógica comum.

Essa regra evita dois extremos ruins: generalizar cedo demais (criando abstrações para um caso que nunca se repete) e nunca generalizar (deixando a duplicação crescer sem controle). Ela existe porque abstrair na primeira ou segunda repetição costuma levar a uma abstração errada — na terceira vez, já se tem informação suficiente para saber o que realmente é comum entre os casos.

📚 Exemplo Completo

Veja como aplicar reutilização e refatoração juntas em um caso realista: processar uma lista de itens de pedido, calcular o total com desconto e avisar quando o cliente é VIP.

Antes (Sem Boas Práticas)

public class P { public void proc(List> l) { double t = 0; for (Map i : l) { double p = (double) i.get("preco"); int q = (int) i.get("qtd"); if (q > 0) { t = t + p * q; } } if (t > 100) { t = t - t * 0.1; } System.out.println("Total: " + t); if (t > 500) { System.out.println("Cliente VIP!"); } } }
Problemas nesta versão:
  • Nomes sem significado: classe P, método proc, variáveis t, p, q
  • Usa Map<String, Object> em vez de um tipo próprio — exige casts frágeis como (double) i.get("preco"), que quebram em tempo de execução se o dado vier errado
  • Um único método faz quatro coisas: somar, aplicar desconto, imprimir e checar VIP
  • Números mágicos (100, 0.1, 500) sem explicação do que representam
  • Impossível reaproveitar só o cálculo do total em outro lugar do sistema sem reaproveitar também a impressão

Depois (Com Boas Práticas)

// ==================== PROCESSAMENTO DE PEDIDOS ==================== public class ProcessadorPedido { private static final double LIMITE_DESCONTO = 100.0; private static final double TAXA_DESCONTO = 0.1; private static final double LIMITE_VIP = 500.0; public void processarPedido(List itens) { double total = calcularTotal(itens); total = aplicarDesconto(total); exibirResultado(total); } private double calcularTotal(List itens) { return itens.stream() .filter(item -> item.getQuantidade() > 0) .mapToDouble(item -> item.getPreco() * item.getQuantidade()) .sum(); } private double aplicarDesconto(double total) { if (total > LIMITE_DESCONTO) { return total - (total * TAXA_DESCONTO); } return total; } private void exibirResultado(double total) { System.out.println("Total: R$ " + total); if (total > LIMITE_VIP) { System.out.println("Cliente VIP!"); } } }

Passo a passo do que mudou e por quê

  • Renomear (2.3): P virou ProcessadorPedido, proc virou processarPedido — agora o nome da classe e do método já dizem o que eles fazem.
  • Tipo próprio em vez de Map: List<Map<String, Object>> foi trocado por List<ItemPedido>, eliminando os casts perigosos e deixando o compilador Java garantir os tipos corretos.
  • Extract Method (2.2): o método original foi dividido em calcularTotal, aplicarDesconto e exibirResultado — cada um faz uma coisa só e pode ser testado isoladamente.
  • Números mágicos → constantes (2.5): 100, 0.1 e 500 viraram LIMITE_DESCONTO, TAXA_DESCONTO e LIMITE_VIP, documentando o que cada valor representa.
  • Loop → Stream API (2.7): o laço manual de soma virou uma cadeia de filter/mapToDouble/sum, mais declarativa e com menos chance de erro de acumulador.
  • Reutilização: agora calcularTotal pode ser chamado de outros pontos do sistema (por exemplo, para mostrar um resumo antes de confirmar o pedido) sem precisar reescrever a lógica de soma.
Melhorias Aplicadas:
  • ✓ Nomes descritivos em toda a classe
  • ✓ Tipo específico ItemPedido em vez de Map<String, Object>
  • ✓ Método dividido por responsabilidade (Extract Method)
  • ✓ Números mágicos substituídos por constantes nomeadas
  • ✓ Cada método faz apenas uma coisa (fácil de testar isoladamente)
  • ✓ Comentário de seção organiza a leitura
  • ✓ Lógica de soma pronta para ser reutilizada em outros pontos do sistema

Refatorar e evitar duplicação não depende só de disciplina — o ecossistema de cada linguagem oferece ferramentas que automatizam refatorações comuns (como Extract Method e Rename) e detectam code smells automaticamente. Abaixo estão as principais ferramentas para Java e para outras linguagens populares, para você reconhecer os equivalentes caso trabalhe em um time multi-linguagem.

✅ Checklist Prático

Antes de considerar o código pronto para revisão ou entrega, verifique os pontos abaixo:

✓ Essa lógica poderia virar um método?
✓ Faz sentido usar herança, interface, composição ou generics aqui?
✓ Já existe uma biblioteca que resolve isso?
Tamanho ✓ Métodos com até 20-30 linhas?
✓ Classes com uma responsabilidade clara?
✓ Poucos parâmetros por método?
Nomenclatura ✓ Nomes explicam o propósito sem precisar de comentário?
✓ Sem abreviações confusas?
✓ Sem números mágicos sem nome?
Segurança da Refatoração ✓ Existem testes cobrindo o comportamento atual?
✓ O comportamento externo continua o mesmo depois da mudança?
✓ Cada refatoração foi feita em passos pequenos?
✓ Há um commit salvo antes de começar, caso precise reverter?
Como usar este checklist:
  • Durante o desenvolvimento: revise mentalmente enquanto escreve.
  • Antes de um commit importante: passe pela lista item a item.
  • Em revisões de código (code review): use como roteiro para dar feedback objetivo.

🔌 Interfaces

Definem um contrato comum entre classes sem parentesco, habilitando polimorfismo.

🔧 Refatoração

Mude a estrutura, nunca o comportamento. Sempre em passos pequenos, com testes.

👃 Code Smell

Sintoma de código mal projetado: duplicação, métodos longos, nomes ruins, condicionais aninhados.

✂️ Extract Method

A refatoração mais comum: mover um trecho com propósito claro para um método próprio.

3️⃣ Regra dos Três

Na terceira repetição de uma lógica parecida, extraia a parte comum.
