CI/CD para front-end

Aula 1 · [SIS]ANO2C3B3S18A1

Conceitos-chave

CI/CD significa Integração Contínua (Continuous Integration) e Entrega/Implantação Contínua (Continuous Delivery/Deployment). Um pipeline de CI/CD automatiza o caminho do código desde o commit até a produção, rodando etapas em sequência sempre que há uma mudança no repositório.

Etapas típicas de um pipeline (ex.: GitHub Actions)

EtapaO que faz
1. Instalação de dependênciasnpm install — prepara o ambiente com tudo que o projeto precisa.
2. Testes automatizadosnpm test -- --coverage — roda os testes; se algum falhar, o pipeline para aqui.
3. Buildnpm run build — só executa se os testes passarem; gera a versão pronta para produção.
4. Deploy automáticoPublica o build em um ambiente como GitHub Pages, Vercel ou Netlify.

Esse pipeline costuma ser configurado em um arquivo ci-cd.yml, dentro da pasta .github/workflows/ do repositório, definindo quando o pipeline roda (ex.: a cada push ou pull request na branch main) e quais etapas ele executa, na ordem.

Por que automatizar isso importa: sem um pipeline, testar, compilar e publicar o código manualmente é demorado e sujeito a erros — é fácil esquecer uma etapa ou publicar código com bugs. O pipeline garante que toda mudança passe pelas mesmas verificações antes de chegar ao usuário.
Situação-problema Uma equipe de desenvolvimento front-end de um e-commerce faz atualizações semanais para melhorar a experiência do usuário e a segurança do site. Como o processo de testar, compilar e publicar o código é manual, é demorado, repetitivo e sujeito a erros — bugs chegam aos usuários e geram insatisfação.

Atividade prática — o que fazer

  1. Preparem um repositório no GitHub com uma aplicação front-end (React, Vue.js ou Angular) e uma estrutura básica de testes.
  2. Configurem um workflow no GitHub Actions (arquivo ci-cd.yml) que rode a cada push/pull request na branch principal.
  3. Adicionem as etapas de instalação de dependências, testes automatizados, build e deploy (ex.: GitHub Pages com a biblioteca gh-pages).
  4. Testem o pipeline com um pull request e corrijam eventuais falhas apontadas nos logs do GitHub Actions.

Testes automatizados para front-end

Aula 2 · [SIS]ANO2C3B3S18A2

Conceitos-chave

Garantir a qualidade de um sistema que muda com frequência é um desafio: cada nova funcionalidade pode quebrar algo que já funcionava. Testes automatizados ajudam a pegar esses erros antes que cheguem ao usuário.

FerramentaTipo de testePara que serve
Jest Teste unitário Verifica se uma função ou componente isolado se comporta como esperado.
Cypress Teste de integração / ponta a ponta (E2E) Verifica se diferentes partes da aplicação funcionam corretamente juntas, simulando o caminho real do usuário na interface.
Pirâmide de testes: cada tipo de teste tem um custo de manutenção e um valor diferente para o projeto. Testes unitários são mais rápidos e baratos de manter; testes de integração/E2E custam mais, mas verificam se o sistema funciona como um todo.
Situação-problema — Sistema de reservas de hotéis Um sistema de reservas de hotéis recebe novos recursos com frequência (filtros de busca, promoções personalizadas). Isso tem gerado bugs em funcionalidades que já estavam estáveis, como exibição de datas e cálculo de preços — erros descobertos só depois que o sistema já está em produção.
Situação — XYZ Comércio Digital (simulação) A XYZ Comércio Digital desenvolve um e-commerce com uma equipe distribuída, em que cada grupo cuida de uma parte do sistema (busca, cálculo de preços, checkout). Ao integrar o trabalho de todos, a equipe percebe que partes que funcionam sozinhas falham quando trabalham juntas: os produtos são adicionados corretamente ao carrinho, mas o preço total no checkout fica errado.

Testes de performance para front-end

Aula 3 · [SIS]ANO2C3B3S18A3

Conceitos-chave

Testes de performance verificam se a aplicação continua rápida e responsiva mesmo sob carga — ou seja, com muitos usuários acessando ao mesmo tempo.

FerramentaPara que serve
Lighthouse (Chrome DevTools)Gera um relatório de performance de uma página: tempo de carregamento, responsividade e sugestões de melhoria.
Apache JMeter / k6Simulam carga e stress, acessando a aplicação repetidamente com um número crescente de usuários simultâneos.

Métricas do Lighthouse

  • LCP (Largest Contentful Paint) — tempo até o maior elemento visível da página carregar.
  • TTI (Time to Interactive) — tempo até a página ficar totalmente interativa.
  • FID (First Input Delay) — tempo de resposta à primeira interação do usuário.
Processo típico: gerar um relatório com o Lighthouse → simular carga crescente (ex.: de 50 até 500 usuários simultâneos) com JMeter ou k6, observando tempo de resposta e taxa de erros → cruzar os dois resultados para identificar gargalos → propor melhorias, como otimizar imagens, reduzir o tamanho dos arquivos JavaScript ou melhorar o cache.
Situação-problema — WebFast A WebFast, um e-commerce conhecido pela alta performance, precisa garantir que a aplicação continue eficiente mesmo com um grande número de usuários simultâneos. A equipe decide implementar testes de carga e análise de performance para medir o tempo de resposta e identificar possíveis gargalos.

Atividade prática — o que entregar

  • Um relatório de performance com as métricas do Lighthouse.
  • Gráficos de carga e tempo de resposta gerados com JMeter ou k6.
  • Uma análise apontando os gargalos identificados e propostas de melhoria.
